# 階段、範圍與推進

## S0：理解與分流

確認這次使用者要完成的任務、目標使用者、核心情境、功能邊界、裝置、設計來源、設計負責人、可用品牌／元件、技術限制及交付格式。先由需求文件與專案取得，避免把全部問題交給使用者填表。

已由 MingMing 整理的需求直接引用版本及 AC（驗收條件）編號，不重寫另一套業務規則。沒有 MingMing 也能獨立開始，只需達到同等的需求清晰程度。

政府標案資訊沿用專案記錄。純設計不例行觸發開發問卷；若已知是政府案，讀可取得的適用設計、可及性、隱私及契約要求。未知防護等級不得自訂，會受影響的身分驗證、資料呈現與權限設計保留待確認。進入程式開發前依使用者全域規範補足分流。

### 三個獨立維度

| 維度 | 選項 | 意義 |
|---|---|---|
| 來源入口 | new-design／continue-wireframe／receive-external | 從哪份現有成果繼續 |
| 設計深度 | lean／full | 探索與製作的工作量 |
| 交付範圍 | wireframe-only／full-design／handoff-only／review-only／scoped-change | 本次完成到哪裡 |

完整外稿不一定 full；高複雜專案的線稿也可能需要 full。不得把預算低解讀成所有檢查都可省略。

### 深度

| 項目 | Lean | Full |
|---|---|---|
| 研究 | 既有資料與必要缺口核對 | 增加來源比較、角色與關鍵旅程分析；真實訪談需另有資料或授權 |
| 視覺探索 | 一個有依據的方向 | 有決策價值才比較兩至三個方向 |
| 畫面製作 | 代表性畫面＋共用規則＋有差異的必要狀態 | 適用關鍵流程、多裝置與重要狀態更完整覆蓋 |
| 原型 | 需要釐清的核心路徑 | 涵蓋關鍵替代、錯誤與恢復路徑 |
| 驗證 | 同樣保留正確性、內容、可及性與範圍檢查 | 加深情境覆蓋；不虛構實際使用者研究 |

沒有固定的頁數或提案數義務。先記錄哪些畫面用實際畫框呈現、哪些採元件狀態／文字規則交付，確保開發不必猜。使用者指定的必交頁面不可自行以代表畫面取代。

S0 完成：問題、目標使用者、範圍、來源、成功條件及重要未知足夠明確。對未知的記錄不是已確認答案。

## S1：流程與線稿

1. 以使用者任務畫操作路徑，包含進入、前置條件、完成與恢復；依據現有業務規則，不自行添加收費、資格、權限或保存政策。
2. 建立資訊結構與畫面清單。使用穩定的 `SCR-*` 畫面 ID 與 `FLOW-*` 流程 ID，連回需求；一個頁面可以有多個狀態。
3. 產出低擬真線稿：先處理內容優先順序、導航、主要行動、欄位與回饋。使用可編輯文字與基本形狀，避免精緻視覺遮掩流程缺口。
4. 為關鍵操作補 loading、empty、error、success、disabled、permission 等適用狀態；不是每個靜態畫面都必須擁有全部狀態。
5. 核對寬窄版面的內容順序、長文字、多筆資料與觸控情境。示範內容標註為示意，不把它當實際產品事實。
6. 檢查流程能否完成、失敗後能否恢復、畫面是否涵蓋需求，記錄觀察與修正。

S1 完成：適用流程與狀態可理解，必要問題已解決，版面與互動有可驗證的產物。wireframe-only 到此交付；其他範圍在無未決重大產品選擇時自主進 S2。

## S2：視覺與互動細化

先分類畫面的主要用途：完成任務、閱讀資訊、行銷轉換或作品展示。以這個目的決定密度、層次與動效，不把同一種行銷版型套到所有後台。

依序做有需要的工作：

- 沿用指定品牌、既有 Figma 元件與產品風格。沒有既有方向時，根據實際內容與使用情境提出可解釋的視覺方案；品牌選擇有實質影響且無依據時才請使用者決策。
- 設定最小必要的設計變數：語意色彩、文字層級、間距、圓角、邊界與效果。沿用專案命名；無慣例時可用 `color/text/primary`、`color/action/primary` 等用途名稱。
- 建立重複出現的元件與狀態，優先使用實例；不是所有一次性圖形都要做成元件。
- 先完成一個代表性畫面檢查方向，再延伸到其餘畫面。避免先大量複製有問題的版型。
- 定義變寬、變窄、換行、溢出、表格與導覽的規則。裝置尺寸來自專案；缺少時提出暫定尺寸並記錄，不把固定桌面與手機寬度變成全域業務標準。
- 互動以說明行動與狀態變化為目的。必要時製作可點擊原型，對不可模擬的後端、權限或非同步行為寫清楚替代說明。
- 字型需支援本案語言並可取得；繁體中文檢查缺字、標點換行與英數混排。不得為追求獨特而禁止系統字型或既有品牌字型。

S2 完成：本次要求的可編輯稿、元件與互動規則已製作，視覺與結構檢查有證據。尚未驗證項目必須保留狀態。

## S3：檢查、修正與交接

依 quality.md 檢查當前版本。先解決流程中斷、規則衝突與資訊缺漏，再處理視覺一致性與細節。對新修改只重跑受影響檢查；無相關修改不反覆截圖或繼續無止境潤飾。

交接前讀取目前 Figma 基準，確認檔案／分支、畫框、時間與截圖對得上。依 mingming-handoff.md 寫明 ready 的範圍、缺口及開發驗證義務。

## 特殊入口

### continue-wireframe

先核對既有線稿的需求版本、作者與適用範圍；可用部分直接引用。若缺少流程或重要狀態，先補規格；補畫或改動外部稿仍須在本次授權範圍內。保留原稿，區分原作者與本次補充。

### receive-external

只要求足夠的交接資訊，不要求設計師使用本工作流格式。AI 先從既有文件映射。外稿若只有圖片，能確認視覺但不能確認 Figma 圖層、元件或精確變數；記為限制。是否足以開發依本次契約與範圍，不能宣稱已收到可編輯稿。

### scoped-change／review-only

指定改兩個按鈕時不重做全站品牌；指定審查時只交發現、證據與修正建議，不改 Figma。局部修正完成只驗證該範圍及受影響依賴。

## 狀態與版本

`design-record.md` 使用 `not_started / in_progress / blocked / ready / not_applicable / stale` 記錄適用階段。ready 只表示該階段與範圍已符合條件；not_applicable 必須附理由。review 的 pass／fail／blocked／not_run／not_applicable 是檢查結果，與階段狀態不同。

變更需求、畫面、元件或關聯規則時增加設計 revision，標記受影響的先前檢查 stale；維持未受影響證據。若主元件影響多畫面，檢查所有相關實例或有依據的覆蓋方式，不能只驗證元件本體。

不要自動接收 Figma 最新改動為已核定設計。已交接版本變動時記錄差異、影響的需求與畫面，交由主線判定重開哪些開發工作。
