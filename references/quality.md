# 設計品質與證據

依需求選適用檢查，不以清單項目數代表品質。每項留下範圍、方法、觀察、結果與證據；`pass` 需要真正執行且成功。

## 檢查順序

| 層次 | 核對重點 | 可接受的設計階段證據 |
|---|---|---|
| 需求與流程 | 目標可完成、規則與權限一致、返回與恢復可理解 | 需求對照、流程走查、原型操作記錄 |
| 內容 | 標籤易懂、數值／條件有來源、錯誤有下一步 | 畫面與文案逐項核對 |
| 狀態 | 載入、空值、失敗、成功、無權限與停用適用狀態 | 畫框、元件變體或明確規格 |
| 版面 | 層次、對齊、間距、內容密度、溢出與重疊 | 對應 revision 的實際畫面截圖 |
| 可編輯結構 | 圖層、命名、Auto Layout、元件實例、變數綁定 | 工具實際讀回的結構與 ID |
| 多裝置 | 寬窄版面、重排、導覽、長文字、資料極值 | 指定尺寸畫面與重排規則；有原型才聲稱操作過 |
| 可及性 | 對比、標籤、焦點順序、非色彩提示、減少動態替代 | 設計數值／註記與檢查方法；部分需到開發階段測試 |
| 工程可交接 | 資產、樣式、互動、限制、需求對應、版本 | handoff 與有效來源連結 |

## 避免泛用模板與過度設計

- 視覺選擇需能連回使用情境與內容。卡片、漸層、陰影與特殊字型皆可使用，但要有資訊或品牌目的。
- 操作型後台優先清楚、一致與可掃讀；不用展示網站的滑鼠特效干擾工作。
- 不把「看起來不像 AI」當作唯一驗收條件。也不因來源 Skill 禁止某字型、色彩或版式，就覆蓋本案品牌。
- 動效需說明觸發、目的與減少動態時的替代；不為了套用特效庫增加功能。
- 文案以一般使用者能理解的行動與結果為主；內部 API、MCP、schema 等詞不進產品畫面，除非使用者確實需要它們操作。

## 可及性的分界

先沿用本案明確的適用標準、版本與等級；涉及契約或法規需查核當前官方來源，不能把自訂預設當作正式合規要求。沒有指定時，把可讀性、鍵盤操作意圖、焦點、標籤、替代文字、非色彩提示與減少動態列為一般設計基線。

對比檢查需記錄實際前景／背景值、透明與狀態；有數值結果才能聲稱數值達標。靜態稿能檢查意圖與外觀，不能驗證 DOM 語意、螢幕閱讀器、真實鍵盤操作或縮放後的瀏覽器行為。把這些列入開發驗收，而非全部算設計缺陷或虛報通過。

## 發現的影響

- **blocking**：無法完成核心任務、業務／權限規則不明、必要設計缺漏、錯誤來源或版本。受影響範圍不得 ready。
- **required**：已定義驗收項目未達成，例如指定手機版缺漏、可讀性或元件狀態問題。修正並驗證後才能放行受影響範圍。
- **optional**：沒有違反需求的風格建議，可記錄後交付，不因審美偏好無限迭代。

不得把 required 改標 optional 只為了結案。若使用者改變範圍，記錄實際決策與仍適用的義務。

## 證據粒度

用 assets/review-record.md 記錄本次實際執行的方法。至少指出：

- 設計 revision、需求版本、Figma 檔案／畫面 ID 與檢查時間。
- 觀察的是哪個裝置／尺寸／狀態；截圖與結構資料對應到同一版。
- 工具名稱與實際結果摘要。手動／AI 走查不要編造命令、exit code 或自動測試名稱。
- 修正前問題、修正內容、修正後結果；舊證據留存。
- `reviewer_mode: self-review`，除非真的有獨立 reviewer。AI 模擬使用者情境不是真實使用者測試。

若截圖工具失敗，可繼續規格或結構核對，但視覺檢查標 blocked／not_run。只有結構讀回不能證明畫面無重疊，只有截圖不能證明圖層與互動正確。

## 完成定義

本次範圍中所有適用且必要的檢查通過，未解 blocking／required 為零，版本與交接吻合，才標記 ready。非本次交付的工程檢查明確移交，不假裝已通過。實際的客戶確認若由契約要求，需有客戶確認證據；一般 AI 檢查不創造額外簽核關卡。
